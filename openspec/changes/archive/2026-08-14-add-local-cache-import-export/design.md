## Context

当前本地可恢复数据主要分为两类：

- `electron-store` 管理的应用设置：启动检查更新、网络代理、工作区 query、视图模式、指标设置、策略回测偏好、自选股和交易计算器设置。
- `app.getPath('userData')/kline-cache/v1` 下的历史 K 线缓存 JSON 文件：每个文件按 `sourceId + symbol + period + adjust` series 维度保存 candles、覆盖范围和刷新元数据。

现有架构要求 renderer 通过 `window.stockApi` 调用主进程能力，不能直接读写本地应用数据目录。导入导出涉及文件系统、Electron dialog、设置归一化和缓存文件写入，因此应放在主进程，由 preload 暴露 typed API，ViewModel 负责用户流程编排和结果展示。

## Goals / Non-Goals

**Goals:**

- 提供一次操作导出当前所有本地可恢复数据的能力。
- 提供从备份文件导入本地可恢复数据的能力，并在导入前校验格式、版本和内容。
- 保持历史 K 线缓存现有维度隔离、完整性计算、读取、刷新和清理行为。
- 对导入导出结果提供可理解的摘要，包括导入数量、跳过数量、失败原因和导出文件路径。
- 在导入失败、文件损坏或部分缓存条目无效时，保护现有本地可用数据。

**Non-Goals:**

- 不同步云端数据，也不接入第三方账号或远端备份服务。
- 不导出窗口位置、运行中的 K 线缓存 job、图表加载状态、未保存表单草稿或远端请求的临时响应。
- 不改变远端行情源请求、代理逻辑或策略回测计算逻辑。
- 不引入加密备份、压缩包格式或跨应用兼容格式；这些可以作为后续增强。

## Decisions

### 1. 使用单文件版本化 JSON 备份包

导出文件采用未压缩、未加密的 UTF-8 JSON，建议扩展名为 `.stock-monitor-backup.json`。顶层结构包含 `schemaVersion`、`appId`、`createdAt`、`appVersion`、`sections`、`settings` 和 `klineCache`。

选择 JSON 的原因：

- 现有设置和 K 线缓存都已经是可序列化 JSON，复用成本低。
- 不需要新增 zip/tar 依赖，也避免打包和跨平台文件权限差异。
- 便于单元测试直接构造合法、损坏、旧版本和部分无效的备份包。

备选方案是 zip 包保留原始缓存文件结构。它对超大缓存更友好，但需要新增压缩依赖或平台处理，增加校验和安全边界复杂度。当前先采用 JSON，后续若缓存体积成为问题再演进。

### 2. 主进程提供 `local-cache-portability` 服务

新增主进程服务负责：

- 读取当前设置并通过现有 normalize 逻辑生成可导出 settings snapshot。
- 枚举 K 线缓存目录中的 JSON 文件，读取并校验合法 cache file 后写入备份包。
- 通过 Electron dialog 选择导出保存路径和导入文件路径。
- 导入时先完整解析备份包，校验顶层元数据和各 section，再执行写入。
- 返回结构化结果，供 renderer 展示摘要。

导入预览会生成一次性 `importToken`，主进程只保留已选择文件路径和摘要，不长期持有完整备份内容；用户确认导入时重新读取并校验文件。新的预览会替换旧的待确认会话，导入成功或失败后清理会话，避免大备份长期占用主进程内存。

IPC 和 preload 只暴露 typed API，例如 `exportLocalCacheBackup`、`importLocalCacheBackup` 和可选的 `inspectLocalCacheBackup`。Renderer 不接收任意本地路径去直接读写文件。

### 3. 导入策略默认合并，支持显式覆盖

导入时提供两种策略：

- `merge`：默认策略。导入设置会覆盖同名设置分区；导入 K 线缓存会替换同 series 的缓存文件；备份中未包含的本地缓存保留。
- `replace`：显式确认后执行。先用导入内容重建可恢复数据；备份中未包含的 K 线缓存 series 会被移除，设置恢复为备份值和当前版本默认值的归一化结果。

选择默认合并是为了降低误删风险。覆盖策略满足“重装或换机后完整恢复”的需求，但必须由用户确认。

### 4. K 线缓存导入先 staging 后提交

K 线缓存导入先在临时目录生成待写入文件，并验证每个目标文件路径仍位于缓存根目录内。校验完成后再按 series 写入正式目录。`replace` 策略在 staging 成功后清理正式缓存目录中未出现在备份包里的 series。

若历史 K 线缓存刷新任务仍在进行，导入会返回错误并要求用户完成或取消刷新后重试；导入进行期间新的缓存刷新或清理请求会被拒绝，避免导入和刷新同时写入同一 series。

设置导入应在 K 线缓存写入成功后执行，避免缓存写入失败时已切换工作区设置。若设置写入失败，系统应返回失败结果，并保留已经完成的缓存写入摘要；实现阶段应尽量让设置写入使用现有 `persistSettings` 和 normalize 逻辑降低失败概率。

### 5. 导入后由 ViewModel 刷新本地状态

导入成功后，工作区 ViewModel 需要重新读取 settings，刷新当前工作区状态、自选股、代理草稿、指标设置、策略偏好和交易计算器设置；如果 K 线缓存管理弹窗已打开，还需要重新查询缓存状态。导入过程不得触发远端行情刷新，除非用户随后手动刷新。

### 6. 默认范围和提示策略已经确认

本 change 采用以下默认决策：

- 备份包含所有可恢复本地数据：应用设置、工作区设置、自选股、指标设置、策略偏好、交易计算器设置和历史 K 线缓存。
- 备份不包含 `windowBounds`、运行中任务、图表加载态、未保存草稿或远端请求临时响应。
- 网络代理设置作为应用设置的一部分导出和导入；导入确认摘要需要提示会恢复代理配置。
- 第一版不做压缩和加密，先保持可测试、可审计的版本化 JSON 格式。
- 导入成功后只重新加载本地状态，不自动触发远端行情刷新。

## Risks / Trade-offs

- [Risk] 单文件 JSON 在历史 K 线缓存很大时可能占用较多内存。→ Mitigation：实现时限制单文件读取大小或在结果中提示导出体积；后续可演进压缩包格式。
- [Risk] 备份包来自手工编辑或旧版本，可能包含无效 settings 或 cache entries。→ Mitigation：所有设置走 normalize，所有 K 线缓存 entries 走现有 cache file 校验；无效 entries 跳过并进入摘要。
- [Risk] 导入覆盖策略会删除本地未出现在备份中的缓存。→ Mitigation：覆盖策略必须二次确认，并在确认文案中列出将替换的数据范围。
- [Risk] 跨版本字段变化导致旧备份无法完整恢复。→ Mitigation：`schemaVersion` 保持显式，导入只支持当前声明兼容的版本；未知字段忽略，缺失字段使用当前默认值归一化。
- [Risk] 备份包可能包含大量历史行情数据。→ Mitigation：导出和导入均只在用户显式触发时执行，结果摘要显示缓存条目数和体积，不在应用启动时自动处理。

## Migration Plan

1. 新增备份格式和主进程导入导出服务，不迁移现有本地数据格式。
2. 扩展 IPC、preload typed bridge 和 renderer adapter。
3. 在工作区增加导入导出入口和确认/结果展示。
4. 更新测试和 `CHANGELOG.md`。
5. 回滚时移除导入导出入口和 IPC；现有 settings 与 `kline-cache/v1` 文件不需要变更。
