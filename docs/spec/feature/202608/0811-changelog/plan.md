# 版本更新日志文档

## 背景

当前项目已经形成 `v0.1.0`、`v0.1.1` 两个正式 tag，`package.json` 当前版本也已经预备到 `0.1.2`，但仓库根目录缺少统一的版本更新日志：

- 用户无法从一个稳定入口查看每个版本的主要变化。
- 已发布版本的功能、修复、构建和文档变更分散在 Git commit、tag、README 和 `docs/spec/feature/202608/*/pr.md` 中。
- `v0.1.0` 包含较多初始能力和发布自动化修复，如果不整理成版本级说明，后续发布说明会难以追溯。
- `v0.1.1` 主要是 GitHub Releases 自动更新源固定，需要和 `v0.1.0` 的发布内容区分。
- 当前 `0.1.2` 还没有 tag，应作为未发布版本记录，避免把未发布内容误写成正式 release。

本次目标是在根目录新增标准 `CHANGELOG.md`，按版本整理当前项目可追溯的更新内容。

## 方案概述

采用标准 changelog 文档方案：

- 新增根目录 `CHANGELOG.md`。
- 使用中文发布说明风格，面向用户和维护者，不逐条堆叠内部文件改动。
- 按版本分组：
  - `Unreleased / 0.1.2`
  - `v0.1.1 - 2026-08-10`
  - `v0.1.0 - 2026-08-10`
- 正式版本日期以 Git tag 的合并时间为准。
- 未发布版本不写发布日期，只记录当前 `package.json` 版本对应的待发布内容。
- 每个版本按实际内容选择分类：
  - `Added`：新增功能。
  - `Changed`：行为或配置调整。
  - `Fixed`：缺陷修复。
  - `Build`：发布、打包、自动更新和构建配置。
  - `Docs`：文档更新。
- 不在正文中写 commit hash，避免发布说明噪音；需要追溯时仍可通过 Git 历史查看。

不扩大范围处理：

- 不修改应用代码。
- 不修改 `README.md`、`package.json` 或发布流程配置。
- 不新增自动生成 changelog 的脚本。
- 不回填 GitHub Release 页面的远端 release notes。

## 实现改动

### CHANGELOG.md

- 新增根目录 `CHANGELOG.md`。
- 增加说明文字：本文件记录每个版本的主要更新内容，版本日期以对应 Git tag 的合并时间为准。
- 增加 `Unreleased / 0.1.2`：
  - 记录 package 版本预备为 `0.1.2`。
  - 记录 `docs/spec/` 重新纳入仓库追踪。
  - 记录历史 feature plan 和 PR 文档恢复。
- 增加 `v0.1.1 - 2026-08-10`：
  - 记录自动更新源统一为 GitHub Releases。
  - 记录版本从 `0.1.0` 提升到 `0.1.1`。
  - 记录 `electron-updater` 发布配置固定为 GitHub provider。
  - 记录 README 自动更新说明同步。
- 增加 `v0.1.0 - 2026-08-10`：
  - 记录 Electron 股票行情桌面应用初始化。
  - 记录远端 K 线数据源、数据源管理和网络代理。
  - 记录工作区设置持久化。
  - 记录指标管理弹窗和指标参数配置。
  - 记录分时行情视图、分时自动刷新、K 线/分时源独立保存。
  - 记录应用图标、检查更新入口、发布自动化和打包修复。
  - 记录图表标题重叠、Linux AppImage、Release workflow 等修复。
  - 记录功能 plan/PR 文档整理。

### 资料来源

- `git tag --sort=-creatordate` 确认正式版本边界。
- `git log` 和 tag diff 确认每个版本包含的提交范围。
- `package.json` 确认当前未发布版本为 `0.1.2`。
- `docs/spec/feature/202608/*/pr.md` 提炼功能背景和主要改动。
- 历史提交中的 `docs/spec/feature/202608/0810-timeshare/pr.md` 补充分时能力说明。

## 测试计划(UT)

本次只新增文档，不涉及运行时代码、类型定义、构建配置或测试逻辑。

需要执行：

- `git diff --check`

不需要执行：

- `yarn typecheck`：未修改 TypeScript 代码。
- `yarn test`：未修改业务逻辑或测试逻辑。
- `yarn build`：未修改构建输入或运行时代码。

如后续把 changelog 接入发布脚本或 README 链接，再补充对应脚本测试、文档链接检查和构建验证。

## 影响范围(建议手动测试范围)

### 文档可读性

- 打开根目录 `CHANGELOG.md`，确认版本顺序为未发布版本在前、正式版本倒序排列。
- 确认每个版本的分类标题和条目清晰可读。
- 确认 `v0.1.0` 没有遗漏主要功能：远端行情、代理、持久化、指标、分时、发布自动化、应用图标。
- 确认 `v0.1.1` 聚焦 GitHub Releases 自动更新源，不混入 `v0.1.0` 内容。
- 确认 `Unreleased / 0.1.2` 不写发布日期，不伪装成已发布版本。

### 版本边界

- 对照 Git tag，确认 `v0.1.0`、`v0.1.1` 日期均为 `2026-08-10`。
- 对照 `package.json`，确认未发布版本为 `0.1.2`。
- 对照 `git log v0.1.1..HEAD`，确认当前未发布内容只记录 `M-17` 相关文档恢复和版本预备。

### 格式检查

- 确认 Markdown 标题层级从 `# Changelog` 开始。
- 确认列表没有明显重复、错别字或过长内部实现细节。
- 执行 `git diff --check`，确认没有尾随空白或空白错误。

## 风险与后续

- `v0.1.0` 聚合了从初始化到多个构建修复的大量内容，当前 changelog 采用版本级摘要，不保证逐 commit 一一列出。
- 早期部分变更没有完整 PR 文档，只能结合 Git log、tag diff 和 README 进行归纳。
- 当前 changelog 是手工维护，后续发布新版本时需要在打 tag 前同步更新。
- 如果后续希望自动生成 release notes，可新增脚本或约定 commit 类型，但不属于本次范围。

## 验收标准

- 根目录存在 `CHANGELOG.md`。
- `CHANGELOG.md` 包含 `Unreleased / 0.1.2`、`v0.1.1 - 2026-08-10`、`v0.1.0 - 2026-08-10`。
- 每个版本的更新内容按实际情况归类，不把未发布内容写入正式版本。
- 文档内容覆盖当前项目主要功能、修复、构建和文档变化。
- `git diff --check` 通过。
